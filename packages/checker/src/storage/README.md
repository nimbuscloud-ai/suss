# storage/

This check pairs a store's declared contract (Prisma, Drizzle, raw SQL) with the storage-access effects in the code. It reports code that reads or writes a field the contract does not declare, and it points out declared fields that no code touches.

## Place in the pipeline

`checkAll()` runs it after the `InteractionIndex` is built. It takes summaries with `storage` provider bindings (the schema) and summaries with `storage-access` interaction effects (the reads and writes in the code), and pairs them by `(storageSystem, scope, container, accessPath)`. `scope`, `container` and `accessPath` have to match exactly. `storageSystem` is the one part of the key that can be null on the declared side, and a null there matches whatever engine the access uses. The check emits four field-existence findings (`boundaryFieldUnknown` for the read and write aspects, `boundaryFieldUnused`, plus the write-only variants). It also emits `boundarySelectorMismatch` when a query picks items by something the container does not key on.

## Key files

- `storagePairing.ts:checkStorage` is the main entry point. It accepts a pre-built `InteractionIndex` as an option, so it does not have to walk the summaries again.
- `grounding.ts:groundReferences` works out what a unit reaches when a caller passed the unit its target. A wrapper that takes its bucket as an argument records `{location.bucket}`, which is the parameter and the field inside it. Each call in the run already records which summary it reaches and what it passed, so grounding is a join over the summaries and needs no further walk over source. The pairing pass classifies each container with `parseBoundaryName` in `@suss/ir-core`, the same module the adapter wrote it with, and passes grounding the parsed reference. That way neither side has its own code for writing or reading the braces. A container that is one bare name, `{ORDER_TABLE}`, is a variable the deployment sets and not an argument anyone passes. It is grounded against `metadata.runtimeContract.envVarValues` on the runtimes that run the file. `runtime-config/placement.ts:placeRuntimes` works out which runtimes those are, and `checkRuntimeConfig` uses the same result to scope a `process.env` read.
- `storagePairing.ts:makeFieldUnknownFinding` builds the per-field errors for code that touches undeclared fields.
- `storagePairing.ts:makeFieldUnusedFinding` builds the warning for declared fields no code accesses.
- `schemaAgreement.ts:checkSchemaAgreement` compares two declarations of one table with each other, described below.
- The storage contract comes from each provider's `metadata.storageContract` (the field list and its metadata).

## Two declarations of one table

A project can declare a table twice, such as a Drizzle copy of the tables a Rails schema owns. `checkSchemaAgreement` pairs declared stores with each other on the same key `checkStorage` pairs a store with an access, with a null engine meeting any engine and a workspace agreeing when the other side has none. It skips SQLite, which stores by affinity, and any contract that does not declare every column.

- **The side that speaks for the database is the provider.** A contract with `origin: "dump"` wins, then one with `origin: "migrations"`, then the file whose path sorts first. `source: true` outranks all three. The other side is the copy. When the provider is a dump or marked as the source and the copy is neither, the copy is judged against it. Otherwise either side could be out of date, and the text gives both files without saying which one is wrong.
- **Columns are compared by what the database stores.** That is `column ?? name`, so `blobId: bigint("blob_id")` is `blob_id`. `derived` fields are skipped. A finding side's `field` is the side's own `name`, which is what a printed rule keys on.
- **The primary keys guard the table.** When the keys differ in their columns or their type families, the two may be different databases that each have a table of that name, so the table gets one warning in place of its column findings. When a side declares no primary key, the table is left unchecked.
- **Severities, when one side is a dump or a stated source.** These are errors, since each has an input that fails:
  - a type family that differs, or nullability that differs;
  - a column the copy declares and the database lacks;
  - a NOT NULL column with no default that the copy leaves out;
  - a default the copy declares and the database lacks, on a NOT NULL column.

  The same default on a nullable column is a warning, and so is a foreign key to a different table. A nullable or defaulted column the copy leaves out is not reported, and neither is a default the copy lacks.
- **Severities, when neither side is.** A column or a default on one side only is a warning. Type, nullability and foreign keys keep the severities above.
- **`default` is compared only when both sides state it.** `false` means a reader looked and found no default. A reader that does not read defaults leaves it out, and so does any summary written before the field existed.
- **The type families** are in `SPELLINGS`, matched without case, with every array one family. A type outside them leaves the column unchecked, and the pass lists it in `unchecked` with the reason. `check` does not print that list yet.
- **Two copies of one dump are not compared with each other.** Each is compared with the dump, and comparing the two as well would report every difference twice.
- **Two dumps are never compared with each other.** A dump is the database, so two dumps of one table name are two databases, such as two Rails apps in one monorepo that each have `users`. Nobody could fix what comparing them would report. A copy is still compared with either dump.
- **A dump is compared with declarations only, and never with an access.** `checkStorage` leaves out every contract with `origin: "dump"`. A Ruby write records every keyword key of `create` and `update`, and some of those are attributes the model defines in code: `password` and `password_confirmation` from `has_secure_password`, `*_attributes` from `accepts_nested_attributes_for`, the keys of a `store_accessor`. Against a dump each would be a column the table lacks, and every column no query selects would be unused. A dump also stays out of `checkAll`'s unmatched providers, so a Rails app whose tables nothing declares again does not look mostly unpaired. `groundStorageAccesses` still lists a dump among the providers, so `suss ask` can say what a table declares.

## Gotchas

- **A store declares whether its field list is complete.** `metadata.storageContract.fieldSet` is `"exhaustive"` when the contract declares every field an item has, as a SQL schema does. DynamoDB declares its key attributes and lets every other attribute vary, so its contract sets `"partial"`. A blob sets `"none"`. The check reports a field as unknown only against an exhaustive contract, so one pass handles every store without a branch per product. A contract that leaves `fieldSet` out is treated as partial. An unknown-field error is a claim, and the check should not make it against a contract that never declared its list complete.
- **The provider declares what identifies an item.** `metadata.storageContract.identifies` lists the fields that pick one item out of the container, in the order the store keys on them. A query whose selector uses anything else gets `boundarySelectorMismatch`, since DynamoDB refuses such a request outright. A contract that leaves `identifies` out makes no claim.
- **A container that only says where to look pairs through its callers.** `namesNothing` in `@suss/ir-core` is true of a name that is one hole and nothing else, and `namesAgree` refuses such a name, since a hole matches anything. An access like that pairs with nothing until grounding works out what its callers passed. A caller that passes a literal grounds it to that name. A caller that builds one from a stage prefix grounds it to the same pattern the template states. A caller that passes something nobody can settle grounds nothing. A wrapper nobody calls reaches nothing, and the check does not treat it as reaching everything.

- **A container that is one variable pairs through the deployment.** `{ORDER_TABLE}` does not refer to any argument, so no call site can settle it. The runtime that runs the file settles it: a Worker declares `ORDER_TABLE = "prod-orders-v2"` in its `wrangler.toml`, and the reader records the value beside the name. A file inside two runtimes' scopes reaches both stores, as a module shared between staging and production does. When no runtime in the run sets the variable, it stays unresolved and the access pairs with nothing.

- **A Worker that reads the variable off its argument pairs the same way.** A fetch handler receives its configuration as a parameter, so `env.ORDER_TABLE` records `{env.ORDER_TABLE}` and not `{ORDER_TABLE}`. The runtime fills that parameter, and no call site in the run does. So when a reference goes through an input that a pack marked `role: "config"`, the check reads it as the variable that comes after it. Every other dotted reference is an argument, and only the callers settle those.

- **A secondary index is a boundary of its own.** A DynamoDB global secondary index has its own key fields, so a query through it pairs against the index's contract and not the table's. `accessPath` is the index or alias, and null means the container's own primary key. Findings write it as `Orders#byCustomer`.
- **The pairing key can attribute one access to several stores.** A shared utility file that calls `db.user.findMany()` pairs against every Postgres schema in scope that declares a `user` table. This is intentional, because the same code can serve several deployments.
- **A store whose engine nobody settled still pairs.** A Terraform configuration can set `database_version = var.database_version` on a Cloud SQL instance, or `engine = var.engine` on an RDS instance. The instance is deployed and it has a name, but no file in the repository says which engine it runs. Such a store arrives with `storageSystem` null and pairs with an access on any engine. Dropping it would leave every access that reaches it without a provider. The summary records a gap that says which attribute went unsettled, so a reader can see why the engine is blank.
- **A store that states its engine beats one that does not.** Two declared containers can both cover what one access reached, and only one of them may say it runs PostgreSQL. The one that agrees with the access takes it. This is the "states more of its own name" rule below, applied to the engine as well: a store with no engine covers every engine, so it is the less specific of the two. Two stores with no engine and the same name are still an even contest, and that reports `ambiguousProvider` the way two equally specific names do.
- **When two tables' names both cover an access, at most one of them is right.** A name built at deploy time has a hole in it, so two declared tables can both have names that cover what an access reached. `{Env}-orders-blue` and `prod-orders-{Colour}` both cover `prod-orders-blue`. `pairing/mostSpecificName.ts` gives the access to the table that states more of its own name. When the two state the same amount, the access pairs with neither, and the run reports `ambiguousProvider` listing both. A gap is the better result there. The other table keys on something else, so pairing with it would report a selector mismatch about a boundary the code never reaches.
- **Wildcard reads suppress unused checks.** A call like `db.user.findMany()` (with no `select`) reads everything. When the index sees a wildcard read, the unused-field check skips the table entirely, because the checker can't tell whether the wildcard caller uses a field that looks unused.
- **A wildcard write makes no per-column claim either.** A write arrives as `["*"]` when the payload was built somewhere no summary reads, such as `tags.map(cb)`. Counting that as a write of every declared column makes the strongest claim about all of them, and it once reported an autoincrement `id` as written by code that never touches it. Such a write is recorded as one write of unknown columns. The unused check skips the table, since that write may have covered the column. The write-only check reads the columns an access lists, so a column that another access lists by name is still reported.
- **An access written under another table's query moves to the table it reaches.** A Prisma query that asks for a related record along with its own gets one access per relation, and so does a write whose `data` inserts one. Each access has `interaction.relationPath` set to the relation fields it was written under. The call tells which relation but never which table, so this pass walks the path over the contracts. For each hop it finds the field of that name on the table the call addressed and takes its declared type with any `[]` stripped. That type is the table the access counts against. When a hop is not declared in any contract, as with `_count`, the pass drops the access and does not leave it on the table the call addressed. Counting a field on the wrong store is what makes the unused warnings wrong.
- **A write that moves a join stays on the near side, as a write of the foreign key.** `comment.create({ data: { article: { connect: { id } } } })` sets `Comment.articleId`. Prisma allows `@relation(fields: [...])` on only one side of a relation, so the contract for that side records those columns as the field's `relationKey`, and nothing about the call shows which columns they are. Such an access arrives with `interaction.relationKey` set and no fields. This pass walks every hop but the last to find the table that declares the relation, reads the key off it, and counts those columns there. That is the opposite direction from the nested `create` above, which counts against the table the relation points at. When the contract does not declare a name as a relation, the pass takes the name as a column, so a payload key nobody declared still reports as an unknown field.
- **A many-to-many with no join model still has somewhere to land.** `favoritedBy User[]` declares no foreign key on either side, because Prisma keeps the join itself in a table the schema never spells out. `@suss/contract-prisma` declares that table as its own boundary and points the field at it with `joinContainer`. A `connect`, `disconnect` or `set` on the field then counts as a write of every column that table declares, and the access is kept. A relation whose key lives on the far side with no join table declared, such as an ordinary one-to-many, still writes no column here, and the access is dropped.
- **A column a query filters on is read.** Every reader records the columns a query picks rows by as `interaction.selector`: the keys of a Prisma `where`, the columns a Drizzle `.where(...)` reads off the table, the comparisons in a SQLAlchemy `filter`, the keys of an ActiveRecord `where`, and the columns in a SQL `WHERE`. The pass counts each of them as a read on the table the access pairs with, on a write as well as a read. `deleteMany({ where: { expires: { lt: cutoff } } })` reads `expires` to pick the rows it deletes, so a column that code writes and only ever filters on is not write-only.
- **A query that asks for some columns, or filters on them, is the only read this pass sees.** The suppression above catches a call that asks for nothing, and only that call. This pass cannot see a column the code takes off a record that a query already returned. A codebase that selects nothing and maps everything therefore leaves columns looking unread. The `boundaryFieldUnused` messages say so and stop short of calling the data dead. Field-level access tracing is what would settle it.
- **Default scope collapses in display.** A `scope === "default"` shows up as the bare container name (`User`) in finding messages. Other scopes show up as `scope/User` so that you can tell them apart.
- **Writes get their own check.** A field that is declared and only ever written, never read, is `boundaryFieldUnusedWriteOnly`. That finding is separate from the one for a field nothing touches at all.
- **Field findings reuse the generic `boundaryField*` vocabulary.** Message-bus and runtime-config use the same finding kinds, and the `aspect` field (read/write/construct) tells them apart. Tooling that spans domains can group by kind.
