# storage/

This check pairs a store's declared contract (Prisma, Drizzle, raw SQL) against the storage-access effects in the code. It verifies that no code reads or writes a field the contract does not declare, and it points out declared fields that no code touches.

## Place in the pipeline

`checkAll()` runs it after the `InteractionIndex` is built. It takes summaries with `storage` provider bindings (the schema) and summaries with `storage-access` interaction effects (the reads and writes in the code), and it pairs them by `(storageSystem, scope, container, accessPath)`. It emits four field-existence findings (`boundaryFieldUnknown` for the read and write aspects, `boundaryFieldUnused`, plus the write-only variants), and `boundarySelectorMismatch` when a query picks items by something the container does not key on.

## Key files

- `storagePairing.ts:checkStorage` is the main entry point. It accepts a pre-built `InteractionIndex` as an option, so it does not have to re-walk the summaries.
- `grounding.ts:groundReferences` answers what a unit reaches when the unit was told. A wrapper that takes its bucket as an argument records `{location.bucket}`, the parameter and the field inside it, and each call in the run already says which summary it reaches and what it passed, so the answer is a join over the summaries rather than another walk over source. The pairing pass classifies each container with `parseBoundaryName` in `@suss/ir-core`, the same module the adapter wrote it with, and hands grounding the parsed reference, so neither side spells or reads the braces on its own. A container that is one bare name, `{ORDER_TABLE}`, is a variable the deployment sets rather than an argument anyone passes, so it is grounded against `metadata.runtimeContract.envVarValues` on the runtimes that run the file. `runtime-config/placement.ts:placeRuntimes` works out which those are, and it is the same answer `checkRuntimeConfig` uses to scope a `process.env` read.
- `storagePairing.ts:makeFieldUnknownFinding` generates the per-field errors for code that touches undeclared fields.
- `storagePairing.ts:makeFieldUnusedFinding` generates the warning for declared fields no code accesses.
- The storage contract comes from each provider's `metadata.storageContract` (the field list and its metadata).

## Non-obvious things

- **A store says whether its field list is complete.** `metadata.storageContract.fieldSet` is `"exhaustive"` when the contract declares every field an item has, which a SQL schema does. DynamoDB declares its key attributes and lets every other attribute vary, so it says `"partial"`, and a blob says `"none"`. Only an exhaustive contract can call a field it does not declare unknown, so the same pass runs over both without a per-product branch. A contract that says nothing is treated as partial: an unknown-field error is a claim, and nothing should make it on a contract that never said its list was complete.
- **What identifies an item is a claim the provider makes.** `metadata.storageContract.identifies` says which fields pick one item out of the container, in the order the store keys on them. A query whose selector uses anything else gets `boundarySelectorMismatch`, since DynamoDB refuses such a request outright. A contract that says nothing claims nothing.
- **A container that says only where to look pairs through its callers.** `namesNothing` in `@suss/ir-core` is true of a name that is one hole and nothing else, and `namesAgree` refuses one, since a hole matches anything. So an access like that pairs with nothing until grounding says what its callers passed. A caller that passes a literal grounds it to that name, a caller that builds one from a stage prefix grounds it to the same pattern the template states, and a caller that passes something nobody can settle grounds nothing. A wrapper nobody calls reaches nothing rather than everything.

- **A container that is one variable pairs through the deployment.** `{ORDER_TABLE}` says nothing about any argument, so no call site settles it. What settles it is the runtime that runs the file: a Worker declares `ORDER_TABLE = "prod-orders-v2"` in its `wrangler.toml`, and the reader records the value beside the name. A file inside two runtimes' scopes reaches both stores, which is what a module shared between staging and production does. A variable no runtime in the run sets stays unresolved, and the access pairs with nothing.

- **A Worker that reads the variable off its argument pairs the same way.** A fetch handler is handed its configuration as a parameter, so `env.ORDER_TABLE` records `{env.ORDER_TABLE}` rather than `{ORDER_TABLE}`. What fills that parameter is the runtime rather than any call site in the run, so a reference through an input a pack marked `role: "config"` is read as the variable after it. Every other dotted reference is an argument, and only the callers settle those.

- **A secondary index is a boundary of its own.** A DynamoDB global secondary index has its own key fields, so a query through it pairs against the index's contract, not the table's. `accessPath` is the index or alias, and null is the container's own primary key. Findings write it as `Orders#byCustomer`.
- **Multi-attribution by the pairing key.** A shared utility file that calls `db.user.findMany()` pairs against every Postgres schema declaring a `user` table in scope. That is intentional: the same code legitimately serves several deployments.
- **One name, two tables, and at most one of them is right.** A name built at deploy time has a hole in it, so two declared tables can both be called something that covers what an access reached. `{Env}-orders-blue` and `prod-orders-{Colour}` both cover `prod-orders-blue`. `pairing/mostSpecificName.ts` gives the access to the table that states more of its own name, and when the two state the same amount the access pairs with neither and the run reports `ambiguousProvider` with both of them in it. A gap is the better answer there: the other table keys on something else, so pairing with it reports a selector mismatch about a boundary the code never reaches.
- **Wildcard reads suppress unused checks.** A call like `db.user.findMany()` (with no `select`) reads everything. When the index sees a wildcard read, the unused-field check skips the table entirely, because we can't tell whether a field that looks unused is consumed by the wildcard caller.
- **A read written under another table's query moves to the table it reaches.** A Prisma query that asks for a related record along with its own gets one access per relation, each carrying `interaction.relationPath`, the relation fields it was written under. The query says which relation and never which table, so this pass walks the path over the contracts: the field of that name on the table the query addressed, its declared type with any `[]` stripped, and that is the table the read counts against. A hop no contract declares, `_count` for one, drops the read rather than leaving it on the table the query addressed, since counting a field as read on the wrong store is what makes the unused warnings wrong.
- **A query that asks for some columns is the only read this pass sees.** The suppression above catches a call that asks for nothing, and nothing else. A field the code takes off a record a query returned is invisible here, so a codebase that selects nothing and maps everything leaves columns looking unread. The `boundaryFieldUnused` messages say so rather than calling the data dead, and field-level access tracing is what would settle it.
- **Default scope collapses in display.** A `scope === "default"` shows up as the bare container name (`User`) in finding messages, and other scopes show up as `scope/User` so that you can tell them apart.
- **Writes get their own check.** A field that is declared and only written, never read, is `boundaryFieldUnusedWriteOnly`. That is different from a field nothing touches at all.
- **Field findings reuse the generic `boundaryField*` vocabulary.** These are the same finding kinds message-bus and runtime-config use, and the `aspect` field (read/write/construct) tells them apart. Tooling that spans domains can group by kind.
