# discovery/

Discovery finds code units by matching patterns. Each `DiscoveryMatch` variant has its own handler file. `index.ts` is the dispatcher, and it also runs the dedup pass.

## Place in the pipeline

Discovery runs after the bootstrap pre-filter has decided which files each pack applies to. It takes a parsed `SourceFile` and the pack's `DiscoveryPattern[]`, and it produces `DiscoveredUnit[]`, one per code unit the patterns recognized. Its output goes to the terminals and effects extraction layer, then the closure walk, then summary assembly.

## Key files

- `index.ts:discoverUnits` is the public API. It runs every pattern, then dedupes the results by `(func, kind, packageExportInfo, routeInfo)`.
- `index.ts:runPattern` is a dispatch table from `match.type` to the per-handler module.
- `shared.ts:DiscoveredUnit` is the result type. It has `func`, `kind` and `name`, plus optional payloads that depend on the pattern (`callSite`, `operationInfo`, `resolverInfo`, `packageExportInfo`, `routeInfo`).
- `decoratedMembers.ts:decoratedCallablesOf` returns the decorated callables a class declares, whether they are written as methods or as properties that contain a function. Both decorator-driven handlers read a class through this.
- `shared.ts:findEnclosingFunction` and `toFunctionRoot` are AST helpers that most handlers need.
- `resolveValue.ts:functionValueOf` / `objectLiteralOf` / `arrayLiteralOf` / `writtenNodeOf` return the value a handler is looking at, whether it was written out at the position or referred to there by name. Every handler that reads an argument, a property or an iterable goes through these.
- `factoryTracking.ts:trackFactoryBindings` is a binding tracker that respects scope. `packageImport` uses it to follow factory results through one syntactic hop.
- `factorySurface.ts:surfaceMethods` lists the methods on object-literal returns and class declarations. `packageExports` uses it.
- `registrationCall.ts:registrationSubjectsOf` returns the variables in a file that contain the routable produced by a `DiscoveryPattern.match`'s import. Route discovery and mount discovery share it, so both decide which variable is the routable in the same way.
- `wrapperIndex.ts:buildWrapperIndex` scans the same files for the registrations a pack declares through `DiscoveryPattern.wraps`, such as Express `app.use(fn)`, or Hono `app.use(path, mw)` and `app.onError(fn)`. It returns two things. The first is the wrappers as units, so each one is summarized where its code is written. The second is the edge from a wrapped unit to its wrappers. The edge is keyed on the routable the registration was made on, which a unit records in `DiscoveredUnit.registrationSubjectId`.
- `helperIndex.ts:buildProjectHelperIndex` reads the functions the project wrote in front of a pack's library and gives the pack a description of what they do, so the pack's own matchers run at the call site. See "Reading the project's own helpers" below.
- `graphqlWrapper.ts:expandDocumentParameterCallers` turns a project hook in front of `useQuery` into one unit per component that calls it. See "A GraphQL hook in front of the library's" below.
- `mountPrefix.ts:buildMountPrefixIndex` scans every file the pack's gate already applies to for mount calls (`DiscoveryPattern.mount`, Express `app.use`, Hono `app.route`). It builds the index that route discovery uses to put together a mounted router's prefix. When a file refers to the mounted value by name, the index follows it across the file, and it chains through every router it was mounted onto in turn.

## Gotchas

- **The dedup key identifies the function and the boundary.** The key is `(func.file:start-end, kind, bindingSuffix, routeSuffix)`. Offsets are positions within one file, so the file has to be part of the function's identity once the question is asked across a whole run. The binding suffix separates consumer summaries that share an enclosing function but consume different exports, such as `extract` calling both `createTypeScriptAdapter` and its `.extractAll`. The route suffix separates units derived from a registrationTemplate that share a handler but expand to different `(method, path)` pairs.
- **A unit is claimed once per run.** A barrel that re-exports a component reaches the same function as the file that declares it. Without this rule both claims would produce a summary with the same name and the same boundary. The key does not include the file the question was asked from, so the second claim collapses into the first. A route file that re-exports a `loader` keeps both, because the route it serves is part of the key.
- **A re-exported sibling package is read at its source.** Say a barrel in one workspace package writes `export { bindingIs } from "@suss/ir-core"`. Through the sibling's manifest, that resolves to the sibling's built declaration file, and the export table gives `packageExports` a declaration with no body. Building the unit there used to produce a provider with nothing about what the function does, bound under the outer package's name, next to the sibling's own unit on the source function. So `packageExports` maps the declaration back. It finds the manifest above the declaration file and resolves that manifest the same way it resolves its own, from published file to source file. Then it looks the export up by name on the published file and takes the declaration the source file exports under that name. The unit lands on the source function, bound under the outer package's name, and the sibling's own run binds the same function under the sibling's name. The result is one body with a provider summary for each package it can be reached through, the same result a sub-path re-export already gives. A declaration with no source behind it, such as a dependency under `node_modules` or a package that ships only its build, is kept as it is.
- **Per-pattern dispatch isn't pluggable.** Each match type has a hardcoded branch in `runPattern`. Adding a new variant means editing the dispatcher, editing the framework `DiscoveryMatch` union, and writing the handler. There is no generic registry. In exchange, the compiler checks that `match.type` is handled exhaustively.
- **Recognizer-only packs.** A pack with no `discovery` patterns still has its `invocationRecognizers`, `accessRecognizers` and `subUnits` run across whatever units other packs discover. Discovery handlers do not deal with recognizers at all. The adapter pipeline collects them across packs and dispatches them separately.
- **Handlers walk their own scope.** Most of them descend the source file with `forEachDescendant` and apply their own scope rules. `factoryTracking`, for instance, scopes bindings to enclosing functions. The dispatcher does not require any particular kind of walk.
- **A route can outlive its handler.** `func` is null on a unit whose registration states a route and then passes on a handler that the registering function itself received as an argument. There is no chain to follow from there. The summary keeps the boundary, points at the registration (`announcedAt`), and uses an `unreadOutcome` gap to record that nothing about the handler was read. A boundary reported with nothing behind it is more useful than no boundary at all. Every other unresolved argument goes unreported, because a chain nobody has followed yet means a rule is missing and says nothing about the code.
- **A handler asks the fact layer and does not follow values itself.** Reading the syntax at a position gets you as far as an identifier. So a handler passes the value to `resolveValue.ts`, and the fact layer follows it through a property read, an array element, an alias, an import and a barrel. When there are two candidates, it returns neither, and that is what stops a wrong handler from being reported with confidence. A handler run without a `ResolutionStore` therefore finds only what is written out at the position, and the adapter always supplies one.
- **`packageImport` dedup happens at TWO layers.** The first is inside the handler, which collapses repeated calls to the same export within an enclosing function. The second is the dispatcher's bindingSuffix dedup, which handles collisions between patterns. Both layers are needed, and removing either one misses cases.
- **A receiver is whatever the resolution store resolves it to.** `app.get("/health", h)` is a route because `app` comes down to a call of something the pack imports from its own library. That is the only test. So the call does not have to be written in the file that built the app. A helper that receives the app writes the receiver as a parameter, the parameter steps to the argument each caller passed, and the walk ends at the same `express()` call that built the app. The walk is `isWrittenAs` in `@suss/resolution`, closed over its steps, so a helper that passes the app on to a second helper resolves through both without any hop count. When two callers pass two different apps, the walk settles on neither, and the receiver is refused instead of guessed.

  A refused receiver used to be the end of it, and a project reading the summaries could not tell a helper whose routes were dropped from a helper that registers none. Now the registration comes out as a unit with no route on it. It has an `unfollowedCall` gap that records which call was refused and how many apps the walk reached. The handler is still summarized, so somebody who wants to know what the missing route does can read it. The count includes only apps built through the pack's own import. That keeps a parameter to which two callers pass two unrelated objects out of the report.

  The remaining limit is the gate in front of this. Running every receiver in the project through the store would ask the question about every method call in every file. So a file is walked only when it imports the library, and for a helper that import is where its parameter's type comes from. A helper that never mentions the library, such as an untyped JavaScript parameter with no import beside it, is not walked at all. Its routes come from the helper index below, which starts at the call site and not at the helper's own file.
- **Mount composition asks the store, the same as a handler does.** A mount call's target argument goes through `resolveValue.ts:writtenNodeOf`, the same resolution store a handler argument goes through. A router mounted through an import from another file therefore resolves the same way as a handler imported from another file. A mount whose prefix is not a string literal, or whose target the store cannot follow, contributes nothing. `extractRouteInfoFromBinding` applies the same rule to a route's own path.

- **A wrapper's behavior is recorded on the wrapper's own summary.** The metadata on a wrapped unit is a reference. It records which file the wrapper is in and what it is called there, the path pattern the registration narrowed it to, and whether the framework calls it only for a request that threw. Nothing about what the wrapper does is copied, the same way a GraphQL resolver points at a schema document and does not repeat the SDL. Combining the two is a later step, and it will be a rule over this edge.
- **A wrapper that receives the thrown value reads one parameter further along.** Express calls an error handler with `(err, req, res, next)` and a handler with `(req, res, next)`. So for a unit whose pattern declares `wraps.throwParam`, the pack's terminals and its input mapping are shifted past the thrown value. Without that shift, an error handler's `res.status(500)` matches nothing and the summary comes out empty. `wraps.resultParam` shifts the same way for a hook the framework calls with a value it computed first, such as `(result, c)` for a validation hook. It does not say anything about when the hook runs.
- **A wrapper passed to the constructor is found on the construction.** `new OpenAPIHono({ defaultHook })` does not register anything on the app afterwards, so there is no call to find. The index reads the option out of the constructor's options object, following a named object and a spread the same way a route's responses are followed. Every route on that app is already keyed on the construction, so the hook reaches all of them with no scope. The option's value goes through the same resolution as a registered function, whether it is written inline, named, or returned by a project factory. A factory the store cannot follow leaves the same `unfollowedCall` gap on each route.
- **The wrapper index decides which registrations are error handlers, then passes on the units.** Express writes both kinds as `app.use(fn)` and tells them apart by arity. One pattern cannot make that distinction on its own, because the plain declaration also matches a four-argument function. So the index first merges every pack's candidates and keeps the narrowest reading of each call. The walk then adds the remaining ones to what `discoverUnits` found.
- **A wrapper's scope is combined with its router's mount prefix.** `api.use("/v1/*", requireCaller)` writes the scope against `api`, and a route on `api` is reported under whatever prefix `api` was mounted at. Mounting `api` at `/api` turns the route into `/api/v1/things/:id`, while the scope still says `/v1/*`. Compared against each other, the two never match, and a middleware that does run gets dropped. So the index runs the same mount chain through `agreedMountPrefix` that route discovery runs, and the scope comes out as `/api/v1/*`. When the chain has no single answer, for example when two mounts of one router land at different paths, the combination gives nothing and the scope stays as written. The route does the same with its own path in that situation.
- **A wrapper reaches the units registered on the same routable, and no further.** The wrapper registration and the route registration must both resolve to one creation site (`const app = express()`), and that is how they are matched. A helper that received the app resolves its parameter to that same site, so a wrapper registered on the app covers a route registered in the helper. A parameter the store cannot settle, for example when two callers pass two different apps, has no site in common with the wrapper, so the wrapper does not reach those routes. Mount discovery has the same limit for the same reason. Order is not read either. A wrapper registered after a route still records against it, because the index lists what is registered and makes no claim about what runs first.

## Reading the project's own helpers

A service rarely calls a library directly at the point that matters. It writes `registerCrud(app, "users", handlers)` or `sendRequest(env, signer, "Query", body)`, and the library call is one hop away, inside a function of its own where the route and the table are parameters. The call site has the literals and no library. The helper body has the library and no literals. Following the parameters back from the call site works for one caller, but a helper called twice leaves two values in every slot and settles on nothing.

`buildProjectHelperIndex` reads the helper once instead, over the whole project, before any file is walked. It gives a pack a `ProjectHelper`: the helper's parameters in order, and every call its body makes, with each argument written in terms of those parameters. A path built as `` `/${name}` `` from parameter 1 comes back as the text `/{1}`, and `handlers.list` comes back as parameter 2's `list` property. The pack turns that into the discovery patterns and recognizers it used to take as config, and its own matchers then run at each call site, where the arguments are literal.

Four points about the index:

- **One registration is one summary.** When the index expanded a helper, the helper's own body is not read for the same method as well. `registerCrud`'s `app.get(\`/${name}\`, handlers.list)` comes from the call sites. `registerHealth`'s `app.get("/health", () => {...})` still comes from the body, because the index made no template for a handler written out in the helper. Without that rule both would produce the same route, and whichever file the run walked first would decide the unit's name.

- **A pack declares how its helpers are found, and the adapter finds them.** `projectHelpers.find` is either `{ by: "subject" }` or `{ by: "text", contains: [...] }`. The subject search starts at the call site. A function to which the project passes one of this pack's own routables counts as a helper of this pack, whatever the helper's own file imports. That is how a helper whose parameter is typed with a project interface gets read at all. The text search starts at the body. It is for a pack whose library is reached over the wire and so has no import to gate on. DynamoDB's `X-Amz-Target` values all start `DynamoDB_20120810.`, and a file that contains that string is read. Both strings come from the library, which meets the same bar `requiresImport` already meets, so neither puts a project's own vocabulary in the adapter.
- **The pack receives plain data and never an AST.** Everything in `ProjectHelper` is plain values. The same declaration therefore runs on any adapter that implements the reading, and `check:vocabulary` still sees the library's own names only in the pack.
- **Nothing here resolves a value through the store.** A helper's body shows what it does with the arguments it received. Following a name out of the body would give the answer for one caller, and the index exists to avoid exactly that.

The index costs one extra `forEachDescendant` over each helper body, plus a `String.includes` over each walked file's text for a text search. A run whose packs ask for none of this skips it all and returns a shared empty index.

The per-file cache records each helper file as a dependency of every walked file that calls one of the helpers, so editing the helper invalidates its callers' stored summaries and they are walked again.

## A GraphQL hook in front of the library's

Production frontends rarely call `useQuery` directly. They write one hook that picks the client, handles a loading flag or adds telemetry, and every component calls that:

```ts
export const useAppQuery = (query: DocumentNode, options?: QueryHookOptions) => {
  const client = useAppClient();
  return useQuery(query, { ...options, client });
};
```

The document argument at the `useQuery` call is `query`, which is a parameter. So the hook reports one summary, with a gap recording that the argument did not resolve, and the components that do pass an operation reach no library call of their own. In a codebase written this way, that covers most of the operations.

`expandDocumentParameterCallers` reads the hook as one operation per caller. It asks the store `argumentsPassedTo(parameter)`, which returns every call of the hook along with the argument each call passed. It runs that argument through the same sequence of document readers that a direct call's argument goes through, and puts the unit on the calling function. `callSite.methodName` stays the library hook's name, so the pack's response semantics and failure delivery apply to the caller's `const { data, error } = useAppQuery(Doc)` the same way they apply to `useQuery`'s. `returnsCall` on the store decides whether the wrapper passes the hook's result back. It is `isWrittenAs` asked of what the function returns, so a result stored in a name first gets the same answer. When the rules cannot show that a wrapper passes the result back, the unit comes without a `callSite`, and no accessors are read off a result that cannot be traced to the library's call.

When the argument at a call site is itself a parameter of the caller, the caller is a wrapper too, and the same question is asked of it, up to three levels deep. The parameters already expanded are passed along so that a cycle stops. Once every call has produced a unit, the hook's own summary is dropped, since `useAppQuery.query` is not an operation and a gap on it would be a finding about nothing. When some call could not be followed, the hook keeps its summary, and the gap's reason gives how many callers were read and how many were not.

Two things are left out. The wrapper's other arguments may pick a client, and that choice is not read, so an operation goes to whichever service `operationScopes` assigns its file to. And the callers come from the facts alone. A spelling the rules do not cover needs a new rule, and this code does not fall back to a reference search.

## Sibling modules

- `bootstrap/preFilter.ts` decides which patterns get dispatched per file.
- `terminals/` works out what each unit's body responds with, returns and throws.
- `resolve/invocationEffects.ts` runs cross-pack recognizers against the same units.
- `resolve/reachableClosure.ts` extends discovered units transitively into callees.

## When adding a new match type

1. Add the variant to `DiscoveryMatch` in `packages/extractor/src/framework.ts`.
2. Write a handler module in this directory exporting `discover<Kind>(sourceFile, match, kind, resolution?): DiscoveredUnit[]`.
3. Add a branch to `runPattern` in `index.ts`.
4. If the units come with new identity (like `routeInfo` or `packageExportInfo`), make sure the dedup key in `discoverUnits` includes it. Otherwise units that share `func` will be collapsed together.
