### Deferred within consumer-side discovery

- **Template-literal / URL-builder paths** → opaque boundary binding, `lowConfidence` finding.
- **Multiple client calls per function** → first pass: one call site per consumer function, deduplicates on enclosing function.
- **Range-based status matching** → `status >= 400`, `response.ok` conditions produce opaque status predicates today; could be resolved to status ranges in a follow-up.
- **Recursive dependency extraction** → local function calls within the consumer are `invocation` effects, not recursively extracted into their own summaries.
- **axios, tRPC, GraphQL clients** → additive; the mechanism is proven, more packs are data.

### Deferred within Phase 8

- **`axios.create()` instances with `axios({ url, method })` bare-call form and `axios.request(config)`**: only per-verb method calls are matched.
- **Aliased default imports** (`import myAxios from "axios"`): pack matches the conventional `import axios from "axios"` only.
- **Multi-hop wrapper expansion** (helper-of-helper): single hop only.
- **Method-as-parameter wrappers** (`fetch(method, path)`): only path-passthrough is recognised.
- **`BodyS3Location`** in CloudFormation: out-of-line OpenAPI bodies aren't fetched.
- **Raw CDK source**: consume `cdk synth` output instead.
- **Greedy `{proxy+}` paths**: extracted verbatim into the boundary path; the checker doesn't normalise them as wildcards, so consumer calls with concrete sub-paths won't pair against a `/{proxy+}` provider.
- **`!Sub` partial resolution**: `!Sub "${ResourceLogicalId.Arn}"` and parameter interpolations are passed through as their raw template strings. That doesn't matter for path/method extraction, since paths are usually literal in practice, but it does mean integration URIs lose their resource references.
- **`!ImportValue` cross-stack tracking**: silently passed through. We'd want it for graph extraction across stacks, and it isn't needed for behavioural summaries within a single template.
- **Non-HTTP triggers** (`AWS::Lambda::EventSourceMapping`, `AWS::Events::Rule`, `AWS::SNS::Subscription`): would each warrant their own resource-semantics package (`@suss/contract-aws-sqs`, `@suss/contract-aws-eventbridge`, etc.) following the same reader/semantics split as `aws-apigateway`. Out of scope while the focus is HTTP boundaries.

## Decisions log

1. **Single language per invocation.** The tool analyzes one tsconfig at a time. Orchestrating a monorepo is up to the user.
2. **Framework packs are declarative data.** A pack describes patterns, and the adapter interprets them.
3. **The condition extractor is four independent functions.** You can test each one with its own fixtures.
4. **Opaque predicates are explicit.** When decomposition fails, the extractor keeps the source text and marks the predicate opaque. It never drops one silently.
5. **Dependency resolution degrades in stages.** A dependency inside the project gets full extraction. A typed dependency gives type information. An untyped one is opaque. None of this needs config.
6. **ts-morph is the TypeScript foundation.** It is public and stable, and one package gives us the AST, the symbol table and the type checker. We use no SCIP and no LSP.
7. **`RawCodeStructure` is the adapter/extractor boundary.** The extractor never sees the AST, and the adapter never runs assembly logic.
8. **Maps over switch statements** for dispatch on discriminated unions. A `Record<Kind, converter>` enforces exhaustiveness at the type level, and nothing can fall through.
9. **Biome 2.x for linting and formatting.** We use no ESLint and no Prettier. A pre-commit hook (husky + lint-staged) runs `biome check --write` on staged files, and `turbo lint` / `turbo lint:fix` are available at the root. See `docs/style.md` for the full style guide.
10. **`expectedInput` flows through `RawBranch`.** The adapter fills in `RawBranch.expectedInput`, and the extractor copies it to `Transition.expectedInput` during assembly, so nothing patches it in after assembly. This keeps the pipeline contract (adapter → `RawCodeStructure` → extractor → `BehavioralSummary`), and it means any future adapter (Python, etc.) gets field-level comparison for free.
11. **`"client"` vs `"consumer"` in `CodeUnitKind`.** `"consumer"` is for message consumers (Kafka, SQS). `"client"` is for API call sites (fetch, ts-rest `initClient`). The two behave differently: clients branch on the response status and read body fields, and consumers receive messages and produce effects.
12. **Depth before breadth.** Deeper cross-boundary analysis (field-level body comparison, predicate-level transition matching, automatic boundary pairing) comes before more breadth (a Python adapter, React components). Breadth multiplies depth. Adding depth later means a rewrite, and adding breadth later only adds code.
13. **Reduce opaqueness recursively.** When the extractor meets something it can't break down (a call expression, an unresolved reference), it should try to resolve through it: inline the function body, follow the variable chain, look up the type. It uses the same recursive strategy at every level. An opaque predicate keeps the source text, and it is the last resort.
14. **`FrameworkPack` → `PatternPack` (done).** The interface describes discovery patterns, terminal extraction, and binding extraction. It applies equally to frameworks (Express, ts-rest) and runtime APIs (fetch). `@suss/client-web` uses the same interface. We renamed it alongside the response property semantics work (7.9).
15. **Response property semantics belong in the pack (done).** Properties like `.ok` (fetch) and `.body` (ts-rest) relate to the HTTP status code and the response body in ways that depend on the framework or runtime. The pack declares these semantics through `ResponsePropertyMapping[]`, so the adapter resolves derived properties (`.ok` → `status >= 200 && status <= 299`) at extraction time. The checker never needs to know about response shapes that belong to one framework.
16. **Throw-with-status converts to response at extraction time.** When a framework pack extracts a status code from a thrown value, the extractor produces a `response` output instead of a `throw` output. What the consumer sees (the behavioral contract) takes priority over how the code achieves it (the mechanism). This keeps transition IDs stable when a refactor switches between throwing and responding directly.
17. **Stubs produce the same summary shape as extracted code.** Summary generators that don't extract from source (`@suss/contract-openapi`, `@suss/contract-cloudformation`) emit the same `BehavioralSummary[]` shape as the extractor, with `confidence.source: "stub"` set on them. The cross-boundary checker pairs stub providers with extracted consumers without any logic that cares where a summary came from. It pairs by `(method, normalisedPath)` whatever produced each side. That is how a TypeScript axios consumer can be checked against a Stripe / GitHub / internal-team API whose handlers we can't extract from source.
18. **Pack-aware checker via summary metadata.** The body-compatibility checker can't hardcode fetch's `.body` accessor, because axios uses `.data`, ts-rest uses `.body`, and custom packs vary. The adapter writes `metadata.http.bodyAccessors` on each client summary from the pack's response semantics, and the checker reads it. The same pattern works for other knowledge that belongs to a pack (status accessor names through `metadata.http.statusAccessors`, request body accessors, and so on). The keys live under `metadata.http.*`, as decision #25 explains.
19. **Wrapper expansion is a post-pass over the discovered summaries.** Path-passthrough wrappers (`getJson(path)` forwarding to `axios.get(path)`) are recognised after discovery has finished for each file. ts-morph references find callers across the project, and each caller gets a synthetic `DiscoveredUnit` that goes back through `extractCodeStructure` with a synthetic pack. This reuses every existing analysis (terminal extraction, branch tracking, expectedInput) instead of growing a second synthesis path next to it.
20. **Contract-source doctrine is documented separately.** [`docs/packs/contract-sources.md`](../docs/packs/contract-sources.md) covers the reader/semantics layering (a manifest reader builds normalized config, then a resource-semantics package emits summaries), the naming convention for opaque predicates in transcribed external contracts (`<vendor>:<service>:<contract>`), per-transition `metadata` for provenance, and the rule that several platform causes for the same status collapse into one transition, so the consumer does not have to tell them apart. This extends decision #17 with concrete conventions, so that more contract sources (CDK synth, Terraform, transcriptions of vendor docs) follow the same pattern.
21. **`Transition.metadata` is a top-level field.** Every `Transition` has an optional `Record<string, unknown>`, mirroring `BehavioralSummary.metadata`. Stubs use it to attribute platform-injected transitions to the manifest they came from. The checker treats it as opaque payload and ignores it, and inspect and diff render provenance from it. It was added to the IR together with the stub doctrine work. The addition only adds a field and doesn't affect checker semantics.
22. **`BOUNDARY_ROLE` lookup replaces hardcoded provider/consumer kind sets.** The pairing logic used to list `PROVIDER_KINDS = {handler, loader, action, middleware, resolver}` and silently dropped `worker`, `component`, `hook` into `noBinding`. We replaced that with a single `Record<CodeUnitKind, BoundaryRole>` exported from `@suss/behavioral-ir`. Adding a new code-unit kind without a role is now a TS error, and the classification has one source of truth across packages.
23. **zod is the IR's single source of truth.** Behavioral summary types are derived from zod schemas in `packages/behavioral-ir/src/schemas.ts` via `z.infer`, the JSON Schema published for non-TS consumers is generated from the same schemas at build time (`z.toJSONSchema`), and the runtime parsers (`parseSummaries`, `safeParseSummaries`) are exposed for boundary validation in CLI and downstream tools. This replaces the earlier split, where the types were hand-written and the JSON Schema was hand-built and an Ajv test was the only thing keeping the two aligned. The "zero dependencies" line on `@suss/behavioral-ir` is gone, since it now has one peer dependency on `zod ^4.0.0`. The trade-off is that bundlers which inline transitively-reached generic types can produce large `.d.ts` files, so the `safeParse*` return types are annotated explicitly to keep the declarations small (~3 KB instead of ~1 MB).
24. **Status property names come from the pack.** The checker used to match only a hardcoded `"status"` and `"statusCode"` when looking for status-eq predicates in consumer transitions. Now the adapter writes `metadata.http.statusAccessors` on each client summary from the pack's `responseSemantics` (entries with `semantics.type: "statusCode"`), parallel to `metadata.http.bodyAccessors`. The checker reads `statusAccessorsFor(summary)` once per check and passes a `ReadonlySet<string>` through `consumerExpectedStatuses`/`refLooksLikeStatus`. It falls back to the historical `["status", "statusCode"]` for hand-written summaries, and for summaries produced before this metadata existed. This also removes the duplicated `isStatusRef`/`isStatusName` helpers that lived in both `response-match.ts` and `provider-coverage.ts`.
25. **Summary metadata is namespaced by boundary semantics; layered-boundary design is the north star.** HTTP-scoped metadata keys (`declaredContract`, `bodyAccessors`, `statusAccessors`) live under `metadata.http.*` instead of at the top level of `metadata`. The namespace shows their scope, so future GraphQL / Lambda-invoke / queue-message packs can have sibling namespaces of their own (`metadata.graphql.*`, `metadata.lambda.*`, etc.) without migration. Keys that don't belong to any one semantics (`metadata.derivedFromWrapper`, which records where wrapper expansion came from) stay at the top level. The checker is still coupled to HTTP end to end: it uses status codes as the discriminator, the response body as the payload, `(method, normalizedPath)` as the pairing key, and 2xx as the success range. Refactoring that coupling into a `BoundarySemantics` interface waits for a second concrete semantics to force the seams into the open. GraphQL is the planned first target, because it shares a transport with REST while discriminating, carrying payload, and pairing differently. See [`docs/theory/boundary-semantics.md`](../docs/theory/boundary-semantics.md) for the layered transport / semantics / recognition model and what the refactor will look like when it lands.
26. **`@suss/contract-openapi` accepts OpenAPI 3.1.** These changes bring the reader up to the 3.1 spec. `type` can be a string or an array (JSON Schema 2020-12 style), and `"null"` in the array means nullable, so 3.0's `nullable: true` and 3.1's `type: [..., "null"]` both normalize to the same `union<T, null>`. The reader accepts `const` as a shorthand for an enum with one value. It supports `discriminator` on `oneOf`/`anyOf`: when a mapping is declared, each variant's discriminator property is narrowed to the literal that maps to it, so the cross-boundary checker can use the discriminator value to tell variants apart. Range status codes (`1XX`-`5XX`, case-insensitive) are expanded into transitions with `statusCode: null` and `metadata.http.statusRange: { min, max, spec }`. The IR has no range variant on `ValueRef`, so the range lives in per-transition metadata, where inspect and future range-aware checker passes can read it.
27. **Committed coverage is a floor against the tree that commits it.** `npm run check:coverage` compares a fresh run against `HEAD`, the same ref and the same rule `check:dogfood` uses: a number below the one the commit records fails, and a number above it passes and needs no refresh. Nothing compares against `main`, so a merge landing on `main` while a branch is open cannot fail that branch on a package it never touched. That failure happened three times in one evening before this changed. Reading `origin/main` made the gate ask "did this branch lower coverage" and "has main moved since the branch forked" as one question, and only the first is worth failing a build over. CI no longer writes coverage summaries or badges back to any branch. The bot that did raced the merge button (a pull request merged 90 seconds after its own run started, so the refresh landed on `main` instead, where it overwrote the 0.41-point drop the gate had correctly failed on) and left every open branch a commit behind. The author refreshes instead, prompted by the pre-push hook, so a drop lands in the diff a reviewer reads. Fork pull requests now get the same check as same-repo ones, since nothing needs write permission. The one file CI still pushes is `scripts/dogfood-baseline.json` on `main`, raising the floor to what a run there sees; nothing reads that file from `main`, so it cannot invalidate a branch either.
28. **Summary-level confidence is for information only.** `ConfidenceInfo.level` on `BehavioralSummary` measures how well the extractor analysed one side of a boundary (the ratio of opaque to structured predicates, a downgrade from wrapper expansion, and so on). The checker does *not* lower finding severities because of it. The `lowConfidence` finding kind is the right mechanism for uncertainty about one finding, and mixing the two axes would hide both. The human `suss check` output shows `(confidence: medium|low)` next to a provider or consumer side whose confidence is below `high`, so reviewers can weigh findings themselves. Downstream tools can read `summary.confidence` from the JSON output and apply their own policy. See the note in [`cross-boundary-checking.md`](../docs/why/cross-boundary-checking.md), "Confidence is informational, not prescriptive."
29. **Overlapping-provider findings are deduped; divergence is a separate task.** When two or more providers describe the same boundary (an OpenAPI stub, a CloudFormation stub and an extracted handler for the same REST endpoint), each one pairs independently with every consumer, and each source produces the same findings. `checkAll` now runs a dedup post-pass. It collapses findings that agree on `(kind, boundaryKey, description, consumer.summary, consumer.transitionId)` into a single representative, which lists the identifier of every provider summary that contributed in `Finding.sources`. `checkPair` is unchanged: it still handles one pair at a time and emits raw findings, and users who build their own pipelines run `dedupeFindings` themselves. Divergence, where sources *disagree* about whether a status exists or what body shape it has, is out of scope here and tracked as a separate follow-up. The planned design compares each provider with the declared contract (`metadata.http.declaredContract`) instead of comparing providers pairwise. That reuses existing infrastructure and attributes each disagreement to one source.
30. **`.sussignore` for accepted findings.** A standalone `.sussignore.yml` (or `.sussignore.yaml` / `.sussignore.json`) at the project root lists rules. Each rule matches findings by `(kind, boundary, consumer.summary, consumer.transitionId)` and applies one of three effects. `mark` is the default: the finding is shown with a `suppressed (mark): <reason>` annotation and does not count toward the exit-code threshold. `downgrade` drops the severity one level, and the finding still counts toward the threshold at the lower level. `hide` removes the finding from the output entirely. `reason` is a required field. We deliberately added **no** `expires` feature. Dates copied from habit and soft warnings don't stop suppressions from going stale. What helps is the required `reason`, plus future observability (a `suss suppressions list` subcommand and suppression counts visible in CI). Narrow matching is the default and requires the kind AND the boundary or transitionId. Broad matching (`scope: "broad"`) opts in to matching on the kind alone or the boundary alone. We considered two other designs. In-source pragmas were rejected, because findings come from comparing across a boundary and there is no single line to attach them to. Per-summary metadata was rejected, because summaries are regenerated and it would be unclear which copy is the source of truth. `@suss/checker` owns the rule types and the matching logic, and `@suss/cli` handles the file I/O.
31. **Cross-source contract agreement is a two-layer model.** Layer 1 (`checkContractConsistency`) compares each provider's transitions with *its own* declared contract, to ask "is this provider doing what it says it does?" Layer 2 (`checkContractAgreement`) compares the declared contracts *across sources at the same boundary*, to ask "do the OpenAPI spec and the CFN template agree on what statuses exist?" Layer 2 works only on `{statusCode, body}` tuples and never on transitions. That makes it strictly simpler than comparing providers transition by transition, since there are no platform-injected transitions, no conditions and no gap logic. It emits a new `contractDisagreement` finding kind, with one finding per status the sources don't all agree on at a boundary, instead of N×(N-1)/2 pairwise findings. Layer 1 needed a fix for this to work without false positives. The `declaredContract.provenance` marker (`"derived"` vs `"independent"`) lets a pack say whether its contract and its transitions come from the same source. OpenAPI stubs are `"derived"`, so comparing them with themselves would prove nothing and is skipped. ts-rest handlers and CFN stubs are `"independent"`. Stubs now fill in `declaredContract`, which they didn't before, and Layer 2 needs that. This replaces the earlier plan for a "sourceDiscrepancy finding kind". Comparing contract to contract is strictly simpler than comparing transition to transition, and it handles three or more sources the same way it handles two.
32. **Strategic direction: React first, multi-shape contracts as the concepts vision.** suss has shipped HTTP as its only concrete boundary, and it has treated "contract" as meaning "schema" (OpenAPI, ts-rest `responses`, CFN `MethodResponses`). To live up to the platform positioning, both assumptions have to go. React is the next boundary we'll ship. It forces the `BoundarySemantics` refactor, it has the widest adoption, and it declares the least (it has no `defineEmits` / `defineSlots` the way Vue does). In React, no single contract shape is enough. Storybook stories capture canonical scenarios, snapshots capture observations of output, Playwright captures behavioral observations, and Figma captures design intent. Comparing the inferred summary with all four gives the full picture of contract consistency. New docs: [`docs/why/kinds-of-contract.md`](../docs/why/kinds-of-contract.md) (the taxonomy of five shapes, which are schema, examples, tests, snapshots and design, with their epistemic characters: specification, observation, derivation) and [`docs/roadmap-react.md`](roadmap-react.md) (the phased plan: Phase 1 inferred extractor, Phase 2 Storybook stub, Phase 3 Figma stub, Phase 4 cross-shape contract agreement, plus what the rollout commits us to and what it defers). This is design only for now, and there is no code yet.
33. **React Phase 1 in progress.** Phase 1.1 shipped. `@suss/framework-react` recognizes default-exported function components, and it classifies returns of a JSX element, a fragment, a self-closing tag or parenthesized JSX as `render` terminals that record the root element's name. We added the `jsxReturn` TerminalMatch variant to `@suss/extractor`, and the adapter's `tryMatchJsxReturn` extracts the root name into `RawTerminal.component`. A fix along the way: default-export discovery now keeps the function's own name (`export default function UserCard() {}` → identity "UserCard"), where before every file's default export was called "default". Phase 1.2 shipped the `componentProps` input-mapping variant. It walks the first parameter's `ObjectBindingPattern` and emits one `Input` per destructured name (role = name, typeText from the type checker). When the parameter isn't destructured, it falls back to a single Input for the whole object (role "props"). The existing hook recognition in `extractDependencyCalls` picks up `useState`/`useEffect`/etc. for free, because they are variable declarations initialized by a call. They appear in the summary only when something downstream (a condition, an output expression) references the hook's return value. Left for later phases: capturing the nested render tree, analysing event handler bodies, conditional rendering (`cond && <X/>`), custom hooks, class components.

34. **React Phase 1.6 shipped: nested render tree.** `Output.render` gained a `root?: RenderNode` field, where `RenderNode` is a recursive discriminated union `{ type: "element"; tag; attrs?; children } | { type: "text"; value } | { type: "expression"; sourceText }`. The adapter's `jsxToRenderNode` walks JSX elements, fragments and self-closing tags and their children, in source order. It strips text that is only whitespace. Dynamic JSX expression children keep their original source text, so downstream tools can display them without parsing again. Phase 1.6 only extends the IR, and the checker's behavior is unchanged. It prepares for Phase 1.6b (handler references on element nodes) and Phase 2 (comparing Storybook story trees node by node with inferred render trees).

35. **React components are N code units.** A component file produces one `component`-kind summary for the render body. In later phases it also produces one `handler`-kind summary per event-handler prop and one `effect`-kind summary per `useEffect`. They share the component's identity prefix (module and export name) and share state through the hooks they close over. But they have different inputs (props, an event, deps), different outputs (JSX, setState or callback invocations, side effects), and they fire at different times. HTTP already works this way when one file registers several handlers: one Express handler module registers N `app.get/post/...` code units in the same source file. The `BoundaryBinding.semantics` layer tells them apart (`render` vs `handler(name)` vs `effect(index)`). We rejected one big "component lifecycle summary" for everything, because it would mix events that mean different things and lose the information that makes React findings useful.

36. **Jackson concept-design framework is the theoretical ground for the multi-code-unit decision.** Daniel Jackson's concept design (MIT; "Concept Design Moves" NFM 2022, "What You See Is What It Does" SPLASH 2025) describes software as *concepts* (self-contained units with state, actions and a purpose) linked by *synchronizations* (rules of the form "when action A₁ in concept C₁ fires, action A₂ in concept C₂ fires"). Syncs can only restrict behavior and can never enable new actions. The structures map like this: a suss code unit ≈ a concept's action, shared closure or hook state ≈ the concept's state, a boundary binding plus a shared-state reference ≈ a synchronization, and a cluster of units in one React component ≈ a concept instance. We diverge on purpose in two ways. (1) There is no intent or purpose, because suss infers behavior bottom-up. `contractDisagreement` findings are the closest stand-in for "purpose violated". (2) There is no genericity. suss summaries describe one instance and are not reusable design building blocks. We don't adopt the vocabulary ("concept") in full, since that would claim intent declarations we don't support. But the structures line up closely enough to justify treating React components as N units, and by the same argument any future framework that clusters code, such as background workers that share a queue. Referenced in `docs/roadmap-react.md` and `docs/why/kinds-of-contract.md`.

37. **React Phase 1.5 shipped: event handlers as separate code units.** Each JSX event-handler prop (`onClick`, `onChange`, etc.) that resolves to a function written in the component becomes its own `handler`-kind `BehavioralSummary`, with the component's identity prefix. Named locals are called `ComponentName.functionName`. Inline anonymous arrows are called `ComponentName.tag.propName`, with a `#N` suffix when several anonymous handlers have the same `(tag, propName)` key. References that pass a prop along (`onClick={props.onDelete}`) are skipped on purpose, since they invoke handlers defined elsewhere that we don't own. It is implemented as a post-pass in the TS adapter (`synthesizeReactHandlers` in `packages/adapter/typescript/src/adapter.ts`, plus `findHandlerLocations` in `react-handlers.ts`). The pass runs when a `component`-kind summary has a `framework: "react"` boundary binding, so the pattern-pack interface stays declarative. Discovery walks the component's JSX descendants without going into nested function bodies. It resolves identifier references to where they are declared locally, to tell handlers written in the component apart from props passed along. `metadata.react` records the parent component, the element tag, the prop name, and (for named locals) the declaration's own name. Handler summaries get a placeholder `{ protocol: "react", framework: "react" }` boundary binding until the `BoundarySemantics` refactor lands. Effects in handler bodies are still limited to what dependency extraction from variable declarations catches. Bare call statements (`setCount(n); onChange(n);`) aren't recorded as `RawEffect`s yet, and Phase 1.5b follows up on that.

38. **React Phase 1.4 shipped: inline JSX conditionals as structured render-tree nodes.** `RenderNode` gained a `conditional` variant (`{ type: "conditional"; condition: string; then: RenderNode; else: RenderNode | null }`). The adapter's `jsxExpressionToRenderNode` breaks `{cond && <X/>}` down into `conditional(cond, <X/>, null)`, `{cond ? <A/> : <B/>}` into `conditional(cond, <A/>, <B/>)`, and `{cond ? <X/> : null}` into `conditional(cond, <X/>, null)`. It treats the `false` and `undefined` values (React's own ways of rendering nothing) the same way as `null`. For `{cond ? nonJsx : <Fallback/>}` it promotes the JSX branch and wraps the condition text in `!(...)`. `||`, `.map()` calls and identifier references stay as opaque `expression` nodes. The adapter only breaks an expression down when at least one branch is statically JSX, so the structure it records never claims more than it understood. v0 keeps the condition text word for word. Running the existing `parseConditionExpression` over it to produce a structured `Predicate` is a follow-up, and cross-shape checking needs it. The change touches only the IR and the adapter, and the checker's behavior is unchanged.

39. **`PatternPack.subUnits` is the extension point for framework runtime scheduling.** A pack can declare an optional `subUnits(parent, ctx) => DiscoveredSubUnit[]` hook. The TS adapter calls it for each discovered unit whose pack defines it, and runs the returned units through `extractCodeStructure + assembleSummary` with their own terminals and input mapping. Sub-units inherit the parent's boundary binding. The React pack uses it to synthesise event-handler and `useEffect` sub-units, so the adapter doesn't hardcode React strings (`onClick`, `useEffect`, `"react"`). The same hook works for Node `EventEmitter` `.on()` handlers, React class methods, Vue lifecycle hooks and GraphQL field resolvers, or anywhere a runtime schedules user callbacks from one construct in the source. `@suss/adapter-typescript` exposes the context interface `TsSubUnitContext`, with primitives for walking JSX attributes, walking call expressions by name, resolving identifiers and reading array literals. The split between pack and language is now enforced by the structure of the code. The adapter contains no framework strings, and React semantics live entirely in `@suss/framework-react`.

40. **`PatternPack.protocol` is required, and it says which transport class a boundary uses.** It does not say which framework. Each pack explicitly declares what transport its boundaries cross. `"http"` covers everything carried over HTTP (REST / OpenAPI / ts-rest / Express / Fastify / React Router / fetch / axios). `"in-process"` covers boundaries with no network hop (React components and their sub-units, and later custom hooks and work across units inside a module). `"aws-sdk"`, `"queue"` and `"grpc"` can be added when future packs need them. `BoundaryBinding.framework` records the framework separately (`"react"`, `"express"`, etc.). The rename matters because `protocol: "react"` would have been a category error: React has no wire protocol, only an in-process runtime. Making the field required and keeping it for transport keeps the IR's distinction between protocol and framework explicit, even before the `BoundarySemantics` refactor fully separates transport from semantics. Guidance for pack authors lives in [`docs/packs/patterns.md`](../docs/packs/patterns.md#protocol).

41. **Refactor: React sub-unit synthesis moved from `@suss/adapter-typescript` to `@suss/framework-react`.** This replaces the Phase 1.5 placement described in decision #37. The old `react-handlers.ts` file and the `synthesizeReactHandlers` adapter post-pass (gated on `framework === "react"`) are gone. Discovery of handlers and `useEffect` bodies now lives in `@suss/framework-react/src/sub-units.ts`, registered through `reactFramework().subUnits`. The adapter's replacement post-pass (`synthesizeSubUnits`) knows nothing about any framework and dispatches to whichever pack defines a `subUnits` hook. `@suss/framework-react` now depends on `@suss/adapter-typescript` for the context type and the primitives. That makes the coupling explicit: this pack is for React through TypeScript. Other frameworks don't take on that coupling unless they need sub-unit work at the AST level.

42. **React Phase 1.5b shipped: effect-body capture + fall-through terminals.** Two pieces work together. (a) A new `TerminalMatch` variant `{ type: "functionFallthrough" }` lets a pack synthesise a default transition when no explicit return or throw covers the function's exit path. (b) A new adapter pass, `extractInvocationEffects`, looks for bare `ExpressionStatement > CallExpression` and records each as a `RawEffect` `{ type: "invocation"; callee; async }` on the default branch. Packs opt in to fall-through, and it is not always on, because the same language fact (every JS function implicitly returns `undefined`) means different things to different packs. An HTTP handler that doesn't respond is a *bug*, so it keeps `transitions: []` and the gap detector flags it. A React event handler with no explicit return is *normal*, so it gets a default transition that records the body's side effects. The sub-unit scaffolding in the adapter's `DEFAULT_SUB_UNIT_TERMINALS` includes the fall-through match, so every React handler and `useEffect` body gets a default transition without the pack declaring it again. Calls on the same source line as a matched terminal (for example Express's `res.json(body)` written as an expression statement) are filtered out, so one source line never counts as both a terminal and an effect. In v0 all invocation effects go on the default branch. Attributing effects to the branch they sit in (inside an `if`/`for` block) is a Phase 1.5c follow-up.

43. **React Phase 1.6b shipped: JSX attributes on render-tree element nodes.** `RenderNode.element` gained an optional `attrs?: Record<string, string>`, which maps each JSX attribute name to the raw source text of its value. String-literal attributes keep their quotes (`type="button"` → `"\"button\""`). Attributes with an expression value record the full expression text (`onClick={() => setCount(c+1)}` → the arrow source). Boolean shorthand attributes (`<input disabled>`) map to `""`. Spread attributes (`{...props}`) appear as `...exprText` keys. The adapter interprets none of it and only records the attributes. Consumers that care about React event semantics (the planned Storybook-stub matcher, the cross-shape checker) combine `attrs` with the React pack's rule for naming handlers to work out summary references when they need them. This keeps the adapter and the pack in their own lanes: the adapter records what the JSX says, and the pack interprets what it means in React. `attrs` is left out entirely when an element has no attributes, so markup without attributes stays short.

45. **React Phase 3 v0 shipped: cross-shape component/story agreement.** `checkComponentStoryAgreement` in `@suss/checker` pairs Storybook stubs with inferred React component summaries by component name. It emits two finding kinds. `scenarioArgUnknown` fires when a story references a prop the component doesn't declare, which catches renamed props and stale stories. `scenarioCoverageGap` fires when a prop gates a conditional branch in the component's inferred logic and no story supplies it, which is a gap in behavioural coverage. The check walks the structured `Predicate` / `ValueRef` IR through `DispatchTable` maps (per decision #8, no switch statements on discriminated unions) to collect the names of the inputs that gate a branch, and falls back to a regex over the source text for opaque predicates. It deliberately does NOT report a mismatch between an arg's value and its declared type. TypeScript already catches those through CSF3's `satisfies Meta<typeof Component>`, and repeating the check would be noise. The integration test at `packages/cli/src/storybook-integration.test.ts` runs the full pipeline (extract the React fixtures → stub the Storybook fixtures → `checkAll`) and asserts that the expected finding fires on mismatches that occur naturally in the fixtures. Storybook is a proof of concept for the cross-shape machinery, and it is not where the main value is. The interesting screen states live in test runtimes that drive the full app (Playwright / Cypress / portable stories in Vitest), and Phase 4 lists observation-shape stubs as the next area to work on.

44. **React Phase 2 v0 shipped: `@suss/contract-storybook`.** It reads `.stories.ts[x]` CSF3 files through ts-morph and emits one `BehavioralSummary` per story exported by name: `identity.name = ComponentName.StoryName`, `boundaryBinding = { protocol: "in-process", framework: "react" }`, args as `parameter` Inputs with each arg's source text on `shape.ref.name`, one default `render` transition that gives the component, `metadata.component.storybook.{story, component, args, provenance: "independent"}`, and `confidence.source: "stub"`. It covers the three common CSF3 variants (`const meta = {...}; export default meta;`, a direct `export default {...}`, and `{...} satisfies Meta<typeof T>` on the meta, the stories or both), plus args written as shorthand properties. Left for later: parsing `play` functions (the event sequences of an interactive story, which will cross-reference handler sub-units in Phase 3), the per-arg metadata in `argTypes`, resolving a component across files (it currently keeps the identifier and doesn't follow the import to a module path), and CSF1 / MDX / decorators / parameters. This is the first stub outside HTTP and the first target for comparing shapes. It confirms that parsing CSF statically is practical, and it shows the `(component, story)` pairing key that will drive the multi-variant semantics field in the `BoundarySemantics` refactor.

46. **Phase A shipped: three-layer `BoundaryBinding`.** `BoundaryBinding` now has three fields. `transport` is the wire (`"http"`, `"in-process"`, …). `semantics` is a discriminated union (`{ name: "rest"; method; path; declaredResponses? }` or `{ name: "function-call"; module?; exportName? }`). `recognition` is the pack identity (`"axios"`, `"ts-rest"`, `"react"`, `"openapi"`, …). The flat `{ protocol, method?, path?, framework, declaredResponses? }` shape is gone. `@suss/behavioral-ir` exports `restBinding` and `functionCallBinding` builders, and every pack and stub uses them instead of object literals. Checker pairing dispatches on `semantics.name`. REST semantics pair by `(method, normalizedPath)`. Function-call semantics don't pair automatically, which leaves an escape hatch for in-process units like React components and Storybook stubs. Wrapper expansion flags forwarders it could not resolve with an empty `method` / `path` on `rest` semantics, and does not make those fields optional. The `BoundarySemantics<S>` dispatch interface (see `docs/theory/boundary-semantics.md`) is designed but not yet extracted. Narrowing inline on `semantics.name === "rest"` is enough while one variant dominates, and the abstraction lands when GraphQL does. REST behaviour does not change: all 32 test packages pass against the new shape, with migrated fixtures and inline narrowing where they read the binding.

47. **Phase B shipped: GraphQL arc end-to-end.** This is the full path from consumer to resolver, delivered as B.1 through B.10 across the IR, the adapter, the checker and four new packs:
    - **B.1 IR variants.** `Semantics` gained `graphql-resolver({ typeName, fieldName })` for providers (at the resolver level and not the field level, per a design decision) and `graphql-operation({ operationType, operationName? })` for consumers. `@suss/behavioral-ir` exports `graphqlResolverBinding` / `graphqlOperationBinding`.
    - **B.2 `@suss/framework-apollo`.** Code-first resolver discovery for `@apollo/server` / `apollo-server` / `apollo-server-express` through a new `resolverMap` DiscoveryMatch. It walks `new ApolloServer({ resolvers: {...} })`, handles shorthand, inline and `satisfies`-wrapped forms, and maps positional inputs as `(parent, args, context, info)`.

51. **`EffectArg` is a five-variant union that preserves shape even under opacity.** It was originally limited to `string`/`number`/`boolean`/`object`/`array`/`template`/`null`. The IR schema is `args: z.array(z.unknown())`, so at the IR layer the extension only changes TypeScript types, and no migration is needed.

52. **Transitive closure from entry points is the default library-discovery mechanism.** A user asked "why do we need a `DiscoveryMatch` variant for internal orchestrators, isn't function-call already a boundary?", and that made us rethink the original approach of configuring it in a pack. A new `allPositional` InputMappingPattern variant emits one Input per declared parameter (role = name) for reachable library units, because no framework declares roles for them. On the nimbus integration-handler, summaries went from 14 → 30, and the 16 new ones were exactly the orchestrators an earlier AI-quiz pass had flagged as invisible.

54. **Differential fuzzer verifies the correctness principles mechanically.** `@suss/differential` is a private workspace package under `tools/` that we never publish (see [`differential-fuzzing.md`](./docs-internal/differential-fuzzing.md)). It generates programs shaped like handlers from a small AST DSL with fast-check. It extracts each one through the production pipeline (an in-memory ts-morph project plus the target's actual pack), runs the same body in `node:vm` against a fixed battery of requests, and judges the result. A transition whose conditions all evaluate to true on the concrete request, but whose status differs from what was observed, is a `falseClaim` (a violation of correctness principle #2). An observation that no transition and no declared gap allows is `uncovered` (principle #1). The predicate interpreter is three-valued (Kleene). Opaque, dependency and unresolved values evaluate to unknown and abstain, so abstention is never a finding. `suss corroborate` is where we plan to reuse the interpreter. The generator tiers follow the documented soundness boundary. The sound tier's property must hold (a 6,000-program run found nothing). The nested-guard and loop-return gap tiers run *inverted* properties that require the fuzzer to rediscover each documented gap quickly. When a rework closes a gap, the rediscovery test fails, and that tells you to promote the construct into the sound tier. Shrunk counterexamples are pinned in a permanent corpus as (program, request, verdict) triples. The harness works with any pack. Framework syntax is isolated in a `FuzzTarget` (a pack, a terminal renderer, a module wrapper and a vm response stub), and the sound-tier property runs against both Express and Fastify, which shows it checks the adapter and not quirks of Express. The designs for the render boundary (JSX) and a second language are in the doc. The first session found one new, previously undocumented bug in dynamic element-access indexes. `resolveSubject` encoded `obj[key]` with the index expression's *source text*, so a dynamic access looked the same as the static read `obj["key"]` and produced false conditions downstream. The fix in `subjects.ts` turns a literal index (or one that resolves to a const literal) into its string or number value, and makes the whole access `unresolved` for anything else. The summary says less and never makes something up.

55. **Differential fuzzer covers the render boundary; destructured parameters resolve as inputs.** The JSX side of `@suss/differential` (see [`differential-fuzzing.md`](./docs-internal/differential-fuzzing.md)) generates function components with destructured string props, `return null` / `return <jsx/>` guards, and JSX trees with inline `&&` or ternary conditionals. It extracts them through `@suss/framework-react`, runs the same TSX in `node:vm` through `ts.transpileModule` and a stub `React.createElement` (with no dependency on react), and judges the observed render trees against what the summaries claim. The judge is conservative about which trees are admissible. A claim commits to *certain* facts (the root tag, and the tags and text of elements outside conditionals) and allows *possible* facts (the branches of a conditional). `RenderNode.conditional` and `expression` nodes abstain. Decision #38 keeps condition text word for word, so parsing it into structured `Predicate`s is the follow-up that would turn those abstentions into verdicts. A 2,400-component run of the sound tier found nothing. The nested-guard gap reproduces at the render boundary: for `if (o) { if (i) { return null; } }`, the final render transition claims it applies unconditionally while execution returns null. We pinned it as a JSX rediscovery milestone and a corpus entry, so one extraction fix will flip the HTTP and JSX milestones together. Bringing up the JSX judge also found an adapter bug that had to be fixed first. `resolveSubject` returned `unresolved` for destructured *parameters* (`function C({ user })`), so every condition gated on a prop was opaque downstream, even though the input mapping lists each prop as an Input (decision #45's checker had a regex fallback over the source text to make up for it). A binding element whose pattern belongs to a `ParameterDeclaration` now resolves to `input(name)`, which also improves react-router loaders that destructure `({ params })`.

56. **CFG path engine replaces the legacy condition collectors; both documented soundness gaps closed.** `paths/pathConditions.ts` in the TS adapter computes the conditions for each terminal by listing the control-flow paths from entry to terminal over the function's *structured* statement flow. It makes one `RawBranch` per path, which is correctness principle #1 ("every path maps to exactly one branch") implemented word for word. A terminal reached along several paths becomes several transitions, each with its own true conjunction, where before it was one branch with a conjunction that was made up or missing. The differential fuzzer judged every one of these consequences. (a) The **nested-guard gap is closed**: `if (a) { if (b) return X; } Y` gives Y the paths `[¬a]` and `[a, ¬b]`, never `[]` or `¬a ∧ ¬b`, and sibling guards inside a block now gate the code after them. (b) The **loop-return gap is closed by making the loop opaque**. Terminals inside a loop get an opaque "some iteration" condition, and terminals after the loop get an opaque "loop exited" negation. Facts quantified over iterations can't be decided statically, so the engine says less and never makes something up. This settles the roadmap's open question in favor of opaque quantified conditions. (c) The else-exit gap, which had *not* been documented, is closed: `if (a) {...} else { return; } T` now gates T on `a`. (d) Terminals in dead code produce no transitions. Every construct the engine models is structured, so recursive enumeration over the AST is equivalent to a query over the lowered CFG. Materializing explicit `cfgEdge` facts will come with the rules engine, when `mayThrow` / `resolvedPath` / `origin` migrate. The engine is conservative. Functions whose statement flow at the unit level contains `switch` / `try` / labels / `break` / `continue` fall back to the legacy collectors unchanged, and so do functions that go over the budget of 256 paths. Flow inside nested callbacks doesn't count, because the expression-level ancestor walker covers it. `SUSS_PATH_ENGINE=legacy` is the emergency escape hatch. Shapes the legacy collectors handled soundly produce byte-identical condition lists by construction, and therefore stable transition IDs. Parity tests in `paths/pathConditions.test.ts` verify this, along with the unchanged workspace suite of 1,100+ tests. Exactly one pinned test needed updating, because it had pinned the over-constrained nested-guard conjunction. The differential corpus flipped its `gap:nested-guard` / `gap:loop-return` entries to `fixed:*`, and the inverted rediscovery milestones on both boundaries became ordinary "promoted constructs stay sound" properties. That showed the whole corpus cycle (find → pin → fix → flip) working from end to end, and the HTTP and JSX milestones flipped together off one adapter change, as we expected from the shared machinery.

57. **`@suss/datalog` is the shared fixpoint engine; the first two hand-written worklists are now rules.** It is a small semi-naïve Datalog evaluator with stratified negation, written in plain TS with zero dependencies, and its rules are plain data with no DSL strings. It becomes the home for extraction's fixpoint problems, the ones that accumulate facts until nothing changes. So termination and soundness are proven once instead of for each analysis. A negation cycle is a hard error instead of a silently wrong answer, and the rules stay auditable and could run on a different engine. Two migrations shipped with it. (a) The **reachable-closure worklist** (decision #52) is now two rules, reachable-if-entry and reachable-if-called-by-reachable. The pass only emits facts on demand: it scans the reachable frontier it hasn't scanned yet for `calls` edges, evaluates again, and repeats. The output is unchanged, and call-graph facts now exist as data that later analyses can join against. (b) **Re-throw enrichment became transitive** (this replaces decision #53's one-hop deferral). `contributes(u, s)` holds for a unit's own throw terminals, and recursively for whatever the callees inside its rethrow's try block contribute. So in a rethrow chain `A → B → C`, C's literal messages now resolve at A, attributed to the direct callee they came through. The derived set of sources is a strict superset of the one-hop results (the facts for bare re-throw sites still contribute), so existing consumers of the metadata only see additions. Propagating through *plain* calls, where an uncaught exception crosses frames with no try, is the full may-throw analysis and remains a follow-up. So does materializing the CFG path engine's edges as facts in the same database. The longer-term payoff: analyses written against the shape of facts (`calls`, `throwsDirect`, `handles`, …) don't depend on the language, so a second language adapter only has to emit the same facts.

58. **The path engine covers the structured language; the legacy fallback is now rare-shape-only.** The engine now models four more constructs. Switch statements: case groups get synthetic condition text identical to the legacy collectors', bodies end in a trailing break, and the negations after the switch are classified by the exit kind of the group body, so catch-all terminals stay the default transition. try/catch: catch bodies get exactly the legacy collector's opaque `catch` condition, because which throw fired can't be decided statically, so the engine abstains. A catch that falls through splits the terminal after the try by route, and `finally` is allowed only as pure cleanup. Loop `break` / `continue` end a path, and the continuation after the loop is computed separately and is already opaque. And arrows with an expression body. The legacy collectors remain only for labeled statements, `finally` with exits or terminals, switch fallthrough into a non-empty clause, switch breaks that are not trailing, and the path budget. No pinned test had to change at the cutover. The rule of matching the legacy collectors (byte-identical conditions on shapes they handled soundly) held for both changes. Next on this track: emit the enumeration's edges as facts into the datalog database each extraction builds (one fact store shared by the reachable-closure, rethrow and future boundary-effect passes), and delete the legacy collectors once the list of declined shapes is empty or explicitly accepted.

59. **The legacy condition collectors are deleted; the path engine is the only condition engine.** `collectEarlyReturns` and the statement-level role of the ancestor walk are gone, along with the `SUSS_PATH_ENGINE` escape hatch, and `computePathConditions` now handles every function. The shapes it declines are labeled statements, `finally` with exits or terminals, switch fallthrough into a non-empty clause, switch breaks that are not trailing, and functions over the path budget. Those no longer fall back to the old collectors. They **degrade** to the conditions of whatever encloses each terminal, since ancestor branches gate it no matter how odd the flow is, plus one opaque "unmodeled control flow" conjunct. So those transitions abstain and don't claim a complete set of conditions. We removed the fallback instead of keeping it because the legacy collectors were unsound on exactly the shapes they still handled. A function with a labeled statement and nested guards got the same missing or over-conjoined negations the path engine was built to fix. The choice was between claims that are sometimes wrong and saying less than we know, and the constitution picks saying less every time. The expression-level ancestor walker stays, because the path engine uses it below the statement level. The 632-test adapter suite and the differential fuzzer both pass. The tests in `conditions.test.ts` that pinned the legacy limitations were rewritten to pin the sound behavior for each path.

60. **One shared fact database per extraction; boundary effects derived as rules.** `extractAll` now creates a single `ClosureFacts` store (`{ db: Database; unitKeyBySummary }`, `resolve/boundaryEffects.ts`). The reachable-closure pass fills it (`entry`, `calls`, plus the map between summaries and unit keys), and later passes read from it. The first reader is `deriveBoundaryEffects`. It adds one `unitEffect(unit, kind, target)` fact per effect on any transition and derives `reachFrom` / `boundaryEffect` with three rules. Every effect reachable statically behind an entry point ends up on that entry's summary as `metadata.effectsClosure: Array<{ kind, target, transitive }>`, sorted so the output is stable, with `transitive: true` when the effect is on a callee and not on the entry itself. This is the raw material for cascade analysis across boundaries: join a provider's effects closure against the identities of other boundaries to see which promises depend on which. It is also the architectural template for putting facts first. Extraction emits facts, rules derive new ones, and assembly stamps the results onto summaries, so rules never touch the AST. Re-throw enrichment still builds its own database with keys based on line numbers. Moving it onto the shared store (one key scheme, one `calls` relation) is the noted follow-up.

61. **`suss corroborate` is a CLI verb (experimental).** The corroboration engine can now be run from the command line: `suss corroborate --experimental -p tsconfig.json -f express [-o annotated.json]`. The engine does rejection sampling against a summary's own conditions with the three-valued interpreter as the oracle, runs the code in a vm with a stub responder, and records `observed` / `refuted` / `untested` verdicts on `transition.confidence.corroboration`. The command re-extracts with the cache disabled, because the sandbox needs the loaded Project. It corroborates every summary in scope and prints a report for each boundary in prose, with the claims that held, were refuted or were not tried, and the counterexamples inline. It can also write the annotated summaries. It exits non-zero when any claim is refuted, since a refuted claim is a finding, the same contract as `check`. 62. **`@suss/framework-drizzle` is the second relational-storage pack, built on the storage-access channel.** Like the Prisma pack, it only has recognizers: no discovery or terminals, and one `InvocationRecognizer` behind a `requiresImport: ["drizzle-orm"]` gate. Drizzle writes queries as fluent chains, so each supported query form has one anchor call that fires exactly once per chain. The anchor is `.from(t)` for select chains, the `insert`/`update`/`delete` call itself, and `.findMany`/`.findFirst` for the relational query API. The pack reads the rest of the chain (`.values`, `.set`, `.where`) with a bounded walk up from the anchor. It checks receivers by type: the symbol's declaration must be under `node_modules/drizzle-orm/`, which covers every driver entry point and transaction handle without hardcoding any of them. To get the table identity, the pack resolves the table identifier back to its `pgTable("users", ...)` declaration and takes the first string argument, which is the SQL table name. That is deliberately a different pairing channel from Prisma's PascalCase model names, because a Drizzle schema is written in SQL terms. When the declaration can't be resolved, the pack falls back to the identifier's own name, which is accurate and never invented. `.where(...)` selectors read the column property accesses on the table expression (`eq(users.id, id)` → `["id"]`), because Drizzle filters are operator expressions and have no object keys. The integration test is in the CLI (`drizzleIntegration.test.ts`). It runs an Express handler with Drizzle calls through the production adapter and checks that the interactions end up on the handler's transitions. It runs entirely in memory, since Drizzle's schema is TypeScript and needs no generate step. Out of scope for v0, and documented in the pack: raw `db.execute(sql\`...\`)`, join clauses as second effects, and `alias()` self-joins.

63. **Prisma and Drizzle storage accesses correspond through declared physical table names.** The two packs' `table` channels differ on purpose. Prisma uses model names (`User`) and Drizzle uses SQL names (`users`). By default they already agree, because a Prisma model's physical table IS its model name. The one exception is `@@map("users")`, and the schema states the exact string, so connecting the two needs no guessing. `@suss/contract-prisma` now reads `@@map` into `metadata.storageContract.physicalTable` (only when it differs from the model name), and the checker's relational pairing matches accesses on EITHER the binding's table or that alias. A Drizzle consumer that touches `users` and a Prisma consumer that touches `User` end up on the same mapped provider. Field-unknown findings fire across the two tools, and usage from both channels counts for the unused and write-only checks. We deliberately did not add heuristics for plurals or case, since those would be guesses, or field-level `@map`. Both packs emit field names as written in code today, so the column channel is already consistent. Revisit that if a recognizer for raw SQL lands.

64. **Resolution follows a chain only where somebody asked about it; the two dense public corpora run in under half the time.** `@suss/datalog` gains `deriveOnDemand(rules, complete)`, a magic-sets rewrite over `Rule[]`. You say which relations have to come out whole, and every other derived relation gets a companion relation that says which of its rows something is waiting on. That companion becomes the rule's first literal, and demand travels down each body the same way the join binds variables. So a rule that needs `comesTo(y, z)` in order to answer `comesTo(x, z)` says so, and the inner pair gets derived because something asked for the outer one. The rewrite is generated from the rules instead of written out by hand, so the JavaScript rule the adapter adds and anything a pack adds later get the same treatment. A relation nothing asks for is not derived at all. `@suss/resolution` writes the questions a caller asks down as rules (`RESOLUTION_QUESTIONS`) over two asking facts: `wanted(x)` for what a value is, and `wantedOrigin(x)` for where a name came from. The store asserts one of them per query and reads the answers back out of `wantedResolves` and its four neighbours.

    We measured three interleaved pairs per corpus and took medians, with `--no-cache` throughout, comparing one build against the other instead of toggling a flag. twenty-front went 114.7s → 47.7s with datalog 57.4s → 15.0s, saleor-dashboard 53.0s → 23.5s with datalog 32.3s → 9.3s, directus/api 6.1s → 5.4s with datalog 728ms → 74ms, saleor-storefront flat, twenty-server 15.5s → 15.8s because it pays for the demand facts and has almost no chain to skip. Every corpus run uses the resuming store and never a single fixpoint at the end (1069 evaluations on twenty-front, 2003 on saleor-dashboard), so the resume path is what those numbers describe; on a synthetic fact base dense enough to make everything reachable from everything, feeding the same facts in a hundred waves costs the rewrite 1.06x what feeding them at once does.

    Correctness is checked by running both evaluators over the same facts and comparing answers: property tests in `@suss/datalog` over generated rule sets and in `@suss/resolution` over generated fact bases, cold, resumed wave by wave, and with the questions arriving after the facts. Summaries are byte identical on all five corpora and on all 36 fixtures with every pack, and the dogfood counts come out the same with the rewrite on and off. `SUSS_RESOLUTION_ON_DEMAND=0` runs the same rules unrestricted, as the escape hatch.

    The measurement said two things the proposal did not. The magic bookkeeping is the whole story on the corpus that queries most broadly: counting only the relations the rewrite covers, saleor-dashboard still derives 8.9% of what it used to, and 7012 of those 8723 tuples are bookkeeping and not answers. The proposal's gate predicted that figure to the decimal, which is why we ran the gate before building this. The second is that one asking fact was not enough. A single `wanted(x)` covering all five questions made directus/api four times slower in datalog, because "where did this name come from" pulls demand through every call the value's function makes and almost nothing on that corpus asks it; splitting the origin question onto its own fact turned that into a ten times speedup. Demand only helps when each asking fact covers the questions a caller actually asked.

    Here is what this does not do. It leaves the transitive-import gate alone, and that gate is a bigger share of twenty-server than everything here. It does nothing for a corpus where the resolution rules barely fire. It does not touch the reachable-closure or rethrow rule sets, since there is no keyed question to restrict them to. And it does not reduce peak memory. Interning atoms, ranked second in the proposal, still stands and still composes: datalog is 32% of twenty-front and 41% of saleor-dashboard after this.

65. **A query in the resolution store costs only its own question.** Demand entered the database as a fact and stayed there. The store marks itself stale when it asks, so the next file's facts were derived over all the demand accumulated so far, and the thousandth question cost a thousand questions. `deriveOnDemand` now returns `demandDriven` alongside the rules, which says which relations the rewrite restricts, and `clearRelations(db, rules, relations)` empties them without sending the rule set back to the base facts. `retract` cannot do that, since taking a fact out of the database can take away a conclusion drawn anywhere. A caller that passes these relations is saying that nothing outside them was derived from them, and the rewrite guarantees that. The store clears its asking fact and the chain that answered it when a query returns, keeps the files it extracted, and reads the five answer relations through the database's own column index instead of five maps rebuilt after every evaluation.

    We measured three interleaved pairs per corpus and took medians, with `--no-cache` throughout, comparing one build against the other. The table gives wall clock, then CPU seconds, then datalog:

    | corpus | wall | CPU | datalog |
    | --- | --- | --- | --- |
    | twenty-front | 50.1s → 33.8s | 68.9s → 46.4s | 15.2s → 1.0s (30% → 3%) |
    | saleor-dashboard | 22.1s → 12.9s | 29.8s → 20.5s | 9.3s → 0.2s (42% → 2%) |
    | twenty-server | 13.4s → 13.2s | 22.5s → 22.5s | 510ms → 348ms |
    | directus/api | 4.45s → 4.45s | 9.03s → 9.02s | 72ms → 56ms |
    | saleor-storefront | 2.16s → 2.10s | 4.20s → 4.15s | 21ms → 11ms |

    The change exists for the branch that resolves what an export is, which asks about every default export. On saleor-dashboard that branch ran 70.1s wall and 80.9s CPU, with 48.3s of datalog over 2,794 evaluations. With the questions scoped it runs 20.7s wall and 29.7s CPU, with 630ms of datalog, and asking the questions stops being what the branch costs. Summaries are byte identical on both.

    Evaluations go up instead of down, because a question asked twice now derives twice: saleor-dashboard runs 2,029 where it ran 2,003, and rounds go from 5,453 to 9,885. More rounds, each of them small, is what we are aiming for. The answer relations are the one thing a query leaves behind, so a caller that asks about a value it has already asked about reads the answer instead of paying for the chain again.

    Correctness is checked the same way the rewrite was. Property tests in both packages ask a question, read what a caller would read, clear, and compare against a database that kept every question ever asked; `@suss/resolution` compares per question, since the two asking facts reach different answer relations. Summaries are byte identical on all five corpora and on all 30 fixtures with every pack, and the dogfood counts are unmoved.

    Here is what this does not do. A repeated question about the same value derives again instead of getting cheaper. It leaves the transitive-import gate alone, and that gate is now the largest share of twenty-server. And it does nothing for a corpus where the resolution rules barely fire. Datalog is 3% of twenty-front and 2% of saleor-dashboard after this, so interning atoms has almost nothing left to win on the public corpora.

66. **A minor release adds what suss can read; the patch after it buys the time back, and changes no output.** Every capability landed in 0.21.0 cost extraction time: following a value into a parameter about 7%, asking which expression is the app about 12%, and reading a Python declaration wherever it is written more on top. We accepted each cost. When suss cannot read a spelling, the boundary is missing from the output with no gap to say so, so extra cost is something to pay down later and never a reason to skip the case. Nobody had scheduled time to pay it down, which is why #118 sat untouched from August with its cheap wins unread.

    So the releases alternate. The minor adds capability and says in its notes what it cost. The patch that follows optimizes and nothing else, and it carries one invariant that makes it safe to take without reading: **every summary it produces is byte-identical to the minor's**. The 0.20.0 work already shipped each of its eleven steps this way, so the gate exists. What changes is that it now applies to a whole release and not only to a commit. A patch that cannot keep the invariant does not count as an optimization, and it waits for the next minor.

    This gives us more than a tidier changelog. Somebody gating CI on `suss check` can take a patch on sight, because identical summaries mean identical findings. The cost of a feature stays legible, since the minor's notes name it and the patch's notes say what came back. And perf work stops competing with capability work for the same slot, which is the reason it kept losing.
